## 根因与影响

核心 `lib/relationship-fit.ts` 以字符串包含、固定分段分数和单字段存在性作为判断入口，缺乏否定语义、资料粒度和有效性校验。婚育计划被错误绑定到双方 relationshipStatus 是否填写；职业“相同”与“内容行业相近”共用模板。

调用影响涵盖人物档案、社交资料分析，以及 relationship-context 支持的聊天报告与快判适配展示。共同点、六维图、总分和结论都依赖同一计算，不能只改文案或图表遮盖问题。

### 历史报告展示的新增证据

`app/api/miniapp/report/route.ts` GET 在读取 ownedReport 后，每次调用 `loadRelationshipFit(ownerId, report.subjectId)`，将当前档案计算结果覆盖到返回对象的 compatibility。`lib/relationship-context.ts` 读取的是当前已确认档案与当前 accepted facts，不是报告生成时的快照。

因此“没有改旧报告数据库”不等于“旧报告显示内容不变”：仅修改算法或用户更新档案，再打开旧报告，适配块就可能变化。目前模板标题只有“与你合适吗？”，没有区分原报告判断与当前资料重算。不能将这一变化画成新的关系事件或用于证明真实关系变好/变差。

当前调用证据：人物档案 profile 路由直接计算；社交资料 social-profile 路由直接计算；截图 screenshot 路由和报告 report 路由通过 relationship-context 计算。快判模板存在 compatibility 展示，但其完整数据流本次尚未证实，不能将模板存在当作接口已贯通。

整体修复需明确两种不同语义：历史分析保留当时依据与结论；最新资料适配作为独立的当前判断，标识计算版本/所用资料变化，并在有可比较快照时解释变化原因。历史资料缺少快照时不能反向补造“当时分数”。这是追踪功能的必要边界，不是只添加一个免责声明。

## 整体修复要求

1. 每维先判资料有效性和语义范围，再形成带双方依据的判断；否定、冲突、含糊分别处理。
2. 婚育计划、关系意愿独立于“是否单身”参与判断，不为缺少无关字段阻断分析。
3. 职业使用真实交集生成建议；非内容行业不得套用拍摄模板。
4. 省份和城市区分，未来/不合理出生资料保持待核对；不补造城市或年龄。
5. 分数、覆盖度、共同点、结论从同一有效维度结果生成；明确冲突不得被其他高分稀释成无条件推荐。
6. 将六个失败案例转为预期正确行为的回归，并补充否定变体、多重表达、缺失资料及跨页面验证。

按变更安全协议，修改前需确认上述算法与所有消费者的影响范围。不是重新设计人的“价值等级”，也不把资料适配分说成关系成功概率。原档案和旧报告不可静默重写；线上迁移与部署仍需单独确认。
